# 당우안 상세 개발 계획서

> 갱신: 2026-10-08 — 앱·웹 역할 분담(1.3)과 개발 순서(10.1)를 최신 합의로 바꿨다. 2장 데모 설명은 화면·문구 참고용으로 남긴다.

## 1. 개요
### 1.1 목표와 독자
#### 1.1.1 제품 목표
정신건강을 돌보고 필요한 도움에 접근하기 쉽게 만든다. 첫 지원 범위는 우울감·우울증 관련 어려움이다. 사용자는 적게 입력하고, 앱은 자료를 정리해 생활 지원과 진료 준비를 돕는다.
#### 1.1.2 작업 분담
산희님은 제품 방향과 사용감을 판단한다. ChatGPT는 계획·데모와 검토를 담당한다. Claude는 후속 정식 구현과 실행 검증을 담당한다. 사용자의 최신 합의가 이전 AI_RULES·PRD보다 우선한다. 임상적 콘텐츠의 검증은 사용성 검토와 별개로 관리한다.
### 1.2 서비스 구조
#### 1.2.1 두 입구
하나의 서비스·계정·데이터 구조에서 ‘내 마음 알아보기’와 ‘일상에서 도움받기’를 제공한다. 입구는 중증도·진단 여부를 분류하지 않는다. 자유롭게 오갈 수 있다. 첫 버전 대상은 만 19세 이상이다.
#### 1.2.2 성공 기준
사용자가 기록 부담을 적게 느끼는가, 진료에서 이야기할 자료를 만들 수 있는가, 도움 요청과 방문 준비가 쉬워졌는가를 평가한다. 이용 시간을 늘리거나 매일 기록하게 만드는 것은 목표가 아니다.
### 1.3 앱과 웹의 역할
#### 1.3.1 공통 계정과 공통 기록
앱과 웹은 하나의 계정으로 로그인하고 같은 기록을 쓴다. 기록은 공통 기록 구조(고유 기록 ID, 소유 사용자 ID, 경험한 시점·입력 시점·시간대, 출처: 직접 입력/회상 입력/기기 측정, 버거움, 선택 태그·메모, 생성·수정 시점, 충돌 확인용 버전)를 따른다. 한쪽에서 만든 기록은 다른 쪽에서 그대로 보이고, 다른 기기에서 고친 기록은 자동으로 덮어쓰지 않는다.
#### 1.3.2 앱: 간편 기록·기기 데이터 수집
휴대폰 앱은 적은 입력으로 남기는 기록과 기기 데이터 수집을 맡는다. 버거움 한 번 선택으로 기록을 끝낼 수 있고, 인터넷이 없어도 기록하고 나중에 동기화한다. 수면·걸음 수·활동 시간 같은 건강 데이터는 사용자가 항목별로 동의한 경우에만 기기(HealthKit·Health Connect·웨어러블)에서 가져온다(4장).
#### 1.3.3 웹: 전체 현황·진료 준비
웹은 넓은 화면에서 전체 현황을 보고 진료를 준비하는 곳이다. 기간별 기록과 기기 데이터의 출처·누락을 함께 보여 주고(3.3), 진료 메모를 정리·수정·인쇄한다. 웹에서도 기록을 남기고 고칠 수 있지만 기기 데이터 수집은 하지 않는다.
#### 1.3.4 공통
도움 화면은 앱과 웹 모두에서 로그인·저장과 무관하게 열린다(9.1). 두 입구(1.2.1)는 앱·웹 어디서나 같은 의미로 쓴다.
## 2. 데모 범위와 결과 확인
### 2.1 구현 범위
#### 2.1.1 실행 가능한 기능
홈, 오늘의 자동 하루 카드, 선택형 기록, 모드 변경, 상태 요약, 가상 진료처 검색·조건 필터, 진료처 선택, 예약 문의 대본, 복용 기록 추가, 진료 질문 추가, 부탁 문장 수정·복사, 힘든 날 카드 입력, 진료 메모 수정·항목 제외·인쇄, 화면 가리기, 밝은/어두운 테마, 초기화 확인, 도움 연락처 화면을 제공한다.
#### 2.1.2 데모의 한계
기기 데이터·기관·거리는 가상 예시다. 실제 약 정보·척도 해석은 제공하지 않는다. 실제 건강 데이터·위치·서버·예약·주문·자동 메시지·알림과 연결하지 않는다. 입력은 메모리에만 유지되며 새로고침하면 사라진다. 도움 화면의 전화 링크만 실제 통신 기능으로 이어질 수 있다. 정식 구현 기술 스택과 다르게 단일 HTML·CSS·JavaScript로 만든 체험판이다.
### 2.2 사용자 확인 순서
#### 2.2.1 기록과 진료
홈 → 오늘 → 선택 사항 펼치기 → 생활 항목 선택 → 버거움 선택 → 내 상태 → 진료 준비. 새 기록 수·생활 항목 빈도·진료 메모가 일치하는지 확인한다. 약 기록과 질문을 추가하고 요약에 반영되는지 확인한다. 항목 제외 후 인쇄 미리보기를 확인한다.
#### 2.2.2 방문과 부탁
알아보기 → 진료처 찾기 → 온라인 예약 조건 선택 → 가상 기관 선택 → 진료 메모. 오늘 도움 → 부탁 종류 선택 → 문장 수정·복사. 초기화 취소 시 입력 유지, 초기화 확정 시 예시 복귀를 확인한다.
## 3. 화면·입력 설계
### 3.1 홈과 오늘
#### 3.1.1 홈
‘지금 필요한 것부터 시작하세요.’ 두 입구와 진료처 찾기·부탁·진료 메모 바로가기를 제공한다. 모든 주요 화면에 도움 버튼을 둔다.
#### 3.1.2 오늘 기록
버거움 선택 1회로 기록 완료. 감정·생활 기능·불편한 변화·자유 메모는 선택 사항이다. 추가 항목은 저장 전에 선택한다. ‘모르겠어요’와 건너뛰기를 제공한다. 표준 척도가 아닌 자체 입력을 임상 점수로 표현하지 않는다.
### 3.2 자동화 모드
#### 3.2.1 모드
조용히 정리 / 짧게 질문 / 진료 준비 / 오늘 도움. 조용히 모드에서는 질문을 숨긴다. 정식 앱은 질문 빈도·알림을 별도로 설정한다. 앱을 열지 않았다고 기록을 추정하거나 밀린 입력을 요구하지 않는다.
#### 3.2.2 회상 기록
정식 버전에서 최근 며칠 돌아보기를 제공한다. 실제 발생일 또는 기간과 입력일을 구분한다. 회상 입력을 당일 관측으로 바꾸지 않는다.
### 3.3 상태와 진료 요약
#### 3.3.1 정보 계층
기기 측정값, 사용자 보고, 표준화된 척도는 별도 영역이다. 자료 출처·시간대·기간·관측 수·누락을 표시한다. 종합 정신건강 점수·약 적합성 점수는 만들지 않는다.
#### 3.3.2 요약 계산
기록 수와 날짜 수를 구분한다. 여러 입력을 임의 평균하거나 대표값으로 확정하지 않는다. 정식 날짜 단위 집계에는 집계 규칙을 명시한다. 누락은 0·정상·미복용으로 대체하지 않는다. 약 변경 전후 비교는 관찰 기록이며 인과관계가 아니다.
#### 3.3.3 출력
가장 불편한 점, 생활 영향, 기기 자료, 복용 중 경험, 진료 질문을 한 장으로 정리한다. 사용자가 수정·제외·미리보기 후 출력한다. 요약은 실제 협진이나 의료진 검증 결과로 표현하지 않는다. 민감한 공유 링크는 초기 버전에서 제공하지 않는다.
## 4. 실제 휴대폰·워치 연동 계획
### 4.1 필수 제품 기능
#### 4.1.1 우선 데이터
수면 구간·총 시간, 걸음 수, 활동 시간부터 시작한다. 심박·위치 이력 등은 별도 필요성 검토 후 결정한다. 수집 항목별 동의·중지·삭제를 제공한다.
#### 4.1.2 기술 조사 관문
순수 웹에서 모든 기기의 건강 데이터에 직접 접근할 수 있다고 가정하지 않는다. Apple HealthKit·Android Health Connect·웨어러블 제공자 API 각각의 공식 문서에서 지원 환경, 권한, 심사, 동기화 제약을 확인한다. 기기 데이터 수집은 휴대폰 앱(1.3.2)이 맡고 웹은 수집하지 않는다. 앱 형태(네이티브·크로스플랫폼)는 이 조사 결과로 정한다. PWA 설치만으로 건강 데이터 접근이 보장되는 것으로 안내하지 않는다. 구현 가능성 확인 전 특정 기기 지원을 약속하지 않는다.
### 4.2 동기화·품질
#### 4.2.1 정규화
provider, source_device, source_record_id, start/end, timezone, metric, value, unit, synced_at, quality를 유지한다. 동일 측정의 중복·수정·삭제를 처리한다. 수면의 날짜 기준과 시간대 변경을 정의한다.
#### 4.2.2 실패와 복구
권한 거부, 만료, 지원 불가, 기기 미착용, 연결 끊김, 부분 데이터, 재연동 상태를 구분한다. 데이터가 없는 날은 측정 없음으로 표시한다. 자동 하루 카드를 사용자 확인 없이 본인 보고로 저장하지 않는다.
## 5. 진료처 검색과 비용
### 5.1 찾기와 예약 준비
#### 5.1.1 위치
‘내 주변 찾기’ 버튼에서 일회성 위치 요청. 상시 위치 추적은 하지 않는다. 권한 거부·오류 시 동네·역 입력으로 전환한다. 정확한 위치는 기본 저장·분석·로그 전송하지 않는다. 지도 제공자로 전송되는 항목은 사전 설명한다.
#### 5.1.2 후보와 필터
정신건강의학과·정신건강복지센터를 구분한다. 거리·진료 시간·초진 접수·온라인 예약 여부의 출처와 확인 시점을 유지한다. 예약 가능 시간을 실제 확인 없이 표시하지 않는다. 외부 예약 페이지 이동과 앱 안 예약 완료를 구분한다.
### 5.2 비용
#### 5.2.1 표시 기준
기관 또는 공식 공개자료로 확인한 비용만 표시한다. 초진/재진, 급여/비급여, 검사·약값 포함 여부, 적용 조건과 날짜를 명시한다. 가격 범위도 근거가 있어야 한다. 자료가 없으면 ‘기관 확인 필요’와 문의 대본을 제공한다. 전체 본인부담금을 추정해 확정 가격으로 제시하지 않는다.
## 6. 약 정보와 경험 기록
### 6.1 약 정보
#### 6.1.1 데이터 원칙
제품명·성분명, 공식 허가 용도, 부작용·주의사항, 공식 자료 링크와 확인 날짜를 제공한다. 실제 자료 수집은 식품의약품안전처 등 공식 출처의 제공 방식·사용 조건 확인 후 진행한다. 개인별 약 추천·처방 변경·중단·용량 조언은 제공하지 않는다.
### 6.2 경험 기록
#### 6.2.1 사용자 입력
약 이름·처방받은 일정·시작/변경 날짜·불편한 변화·생활 영향을 기록한다. 정식 구현은 처방 변경 이력을 덮어쓰지 않고 사건별로 보존한다. 체크 없음은 복용 여부 미확인이다. 여러 약 복용과 같은 기간 생활 변화도 분리해 표시한다.
#### 6.2.2 질문 연결
‘이 변화가 약과 관련이 있을까요?’처럼 의료진에게 물어볼 문장을 만든다. 임상적 인과판정 대신 날짜순 정리를 제공한다.
## 7. 일상 지원과 접근성
### 7.1 힘든 날 카드
#### 7.1.1 구성
괜찮은 날 음식·연락 대상·부탁 문장을 미리 설정한다. 연락 대상 등록은 필수가 아니다. 답장 없음·부탁 거절·연락 대상 없음의 다음 선택을 제공한다. 발송은 사용자가 직접 실행하며 복사를 발송 완료로 기록하지 않는다.
### 7.2 사용 원칙
#### 7.2.1 부담 줄이기
매일 기록·출석·배지·평가·죄책감 문구를 사용하지 않는다. 큰 터치 영역, 화면 확대, 키보드·스크린리더, 명도 대비, 동작 줄이기를 검증한다. 의미 없는 강제 축하나 ‘하나면 충분해요’ 같은 단정적 위로는 사용성 검토를 거친다.
#### 7.2.2 개인정보 화면 보호
화면 가리기는 화면 표시만 숨기며 보안 잠금이라고 표현하지 않는다. 정식 버전은 공용 기기 안내, 로그아웃 시 사용자별 상태 제거, 잠금 화면 알림의 민감 내용 숨김을 구현한다.
## 8. 정식 데이터·보안 설계
### 8.1 저장과 이동
#### 8.1.1 선택지
저장 안 함 / 이 기기 / 계정 저장. 저장 위치·공용 기기 위험·삭제 가능성을 안내한다. 계정 저장은 별도 동의를 거친다. 이동은 원본 읽기 → 대상 저장 → 무결성 확인 → 선택적 원본 삭제 순서다. 실패 시 원본 보존·중복 방지·재시도·부분 실패 안내를 제공한다.
### 8.2 데이터 모델 초안
#### 8.2.1 테이블
profiles(최소 설정), consents(항목·버전·시점), checkins(상태·태그·사건 시점), observations(기기 측정), medications(사용자 복용 기록), medication_events(변경 이력), questions, appointments, support_cards, integration_connections(연동 상태), deletion_jobs(삭제 처리 상태). 각 사용자 데이터에는 owner_id와 시간대·생성/수정 시점을 둔다. 연락 대상은 제3자 정보이므로 최소 수집한다.
### 8.3 보호와 삭제
#### 8.3.1 통제
모든 사용자 테이블에 RLS와 소유자별 접근 통제. 사용자 A/B 간 조회·생성·수정·삭제 거부를 실제 검증한다. 서버의 높은 권한 키로 접근할 때도 소유자 검증을 생략하지 않는다. 비밀 키는 서버 환경에서만 사용한다. 기록·위치·부탁 상대를 외부 AI, 분석 도구, 오류 로그에 보내지 않는다. 데모도 외부 분석 스크립트를 포함하지 않는다.
#### 8.3.2 삭제
기록·첨부·인증 계정·연동 토큰·기기 상태를 대상으로 삭제 절차를 정의한다. 백업 보관·삭제 정책은 별도 고지한다. 부분 실패를 완료로 표시하지 않는다. 데이터 이전과 파괴적 변경은 확인 절차를 둔다.
## 9. 도움 흐름과 콘텐츠 운영
### 9.1 도움 접근
#### 9.1.1 독립성
로그인·기록 저장·결과 계산과 독립된 도움 화면을 제공한다. 자동 감지는 보조 기능이며 위기 상태 판정이나 안전 보장을 하지 않는다. 도움 안내를 강제해 다른 기능을 막지 않는다. 웹의 오프라인 첫 방문에는 다운로드되지 않은 화면 제공을 보장할 수 없으므로 재방문 캐시·다운로드 카드 등 실제 지원 조건을 명시한다.
### 9.2 콘텐츠 출시 조건
#### 9.2.1 검증
약 정보·척도·진료/비용/제도 설명·위기 연락처는 출처와 확인 날짜를 관리한다. 실제 척도는 한국어 판본·사용 조건·응답 기간·계산·미응답·해석 문구 확정 및 전문가 검토 후 공개한다. 개인정보·의료기기 관련 판단은 출시 전 해당 전문가에게 확인한다. 개발 계획서는 법률·의학적 적합성이 확인됐다는 인증이 아니다.
## 10. 개발 순서와 완료 기준
### 10.1 단계
#### 10.1.1 실행 순서
핵심 순서는 **공통 기록 구조 → 웹 실제 저장 → 앱 오프라인 기록·동기화 → 건강 데이터 연동**이다. 앞 단계의 검증이 끝나야 다음 단계로 넘어간다.

| 단계 | 내용 | 상태 (2026-10-08) |
|---|---|---|
| 1. 공통 기록 구조 | 기록 표·동의 표·RLS·중복 방지·버전 충돌 규칙. 앱·웹이 같은 구조를 쓴다. | 구현. 로컬 DB 시험 통과, 실제 Supabase에서 A/B 차단·중복·충돌 일부 확인. 지우기 함수 적용 대기 |
| 2. 웹 실제 저장 | 로그인·동의 후 기록 생성·조회·수정·삭제, 저장 실패 시 입력 유지, 로그아웃 시 화면 비우기 | 구현·배포. 실제 브라우저 끝까지 검증은 미완료 |
| 3. 앱 오프라인 기록·동기화 | 휴대폰 앱에서 간편 기록, 인터넷 없이 저장 후 동기화(같은 ID 재전송, 충돌 시 사용자 선택) | 시작 전 |
| 4. 건강 데이터 연동 | 4장 기술 조사 관문을 거쳐 가능한 제공자부터 연결. 가상·실제 데이터 구분 유지 | 시작 전 |

그 다음 단계(순서는 위 네 단계가 끝난 뒤 다시 합의):
- 웹 전체 현황·진료 준비 화면(3.3)을 실제 기록·기기 데이터로 구현.
- 실제 진료처·공식 약 정보 연결. 출처·갱신·실패 화면 구현.
- 임상 콘텐츠·개인정보 검토와 두 입구 사용자 테스트 후 제한된 베타.

ChatGPT 데모는 화면·문구 참고 자료로 계속 쓴다. 단계 기간은 기기 지원·외부 API·검토 결과에 따라 산정한다. 확정되지 않은 연동을 근거로 일정을 보장하지 않는다.
### 10.2 검증
#### 10.2.1 필수 시나리오
한 번 선택 기록, 추가 입력 없이 완료, 자료 없음·중복·다중 기록, 날짜/시간대 변경, 약 변경 이력, 요약 항목 제외, 위치 거부, 비용 미확인, 외부 이동 취소, 복사 실패, 연결 해제, 사용자 간 권한, 저장/이동/삭제 실패, 도움 화면 독립성, 작은 화면·키보드·200% 확대·인쇄를 확인한다.
### 10.3 Claude 인계 지침
#### 10.3.1 실행 요청
본 계획서를 최신 제품 기준으로 삼는다. 기존 PRD/AI_RULES에서 충돌하는 내용은 최신 합의를 반영해 함께 갱신한다. 기능 하나씩 구현하고 실제 실행 결과를 보고한다. 실제 건강 기록을 코드·로그·테스트 데이터에 넣지 않는다. 지원하지 않는 연결을 완료로 표시하지 않는다. 데모 예시는 정식 기록과 섞이지 않게 분리한다. 변경 파일·검증 결과·남은 제약을 보고한다.
