# D03 계정 삭제 구현 설계 · 2026-10-10

## 1. 목표와 현재 근거
본인 확인을 마친 사용자가 자기 계정과 그 계정의 기록·동의를 삭제한다. 다른 계정 및 운영 데이터를 시험에 사용하지 않는다.
기준 main f30093b4c980d22e4038780e0070e2f0aef607f1. 소스 검토만 완료했으며 구현·실제 삭제·권한 추가는 아직 하지 않았다.
- src/lib/supabase/env.ts는 공개 URL·anon 키만 읽는다. 관리자 클라이언트·계정 삭제 API는 없다.
- 20261007000000_records_v1.sql의 consents.owner_id와 checkins.owner_id는 auth.users(id) ON DELETE CASCADE다.
- 20261008000000_rpc_only_writes.sql의 RPC 전용 기록 쓰기 보호는 유지한다.
- 소스의 외래 키가 실제 테스트/운영 DB에도 동일한지 미검증이다. 운영 반영을 가정하지 않는다.
- 제품 기준은 Library PRD 본문 v3.1 F02/D03. 기존 저장·계정 보호 흐름을 재사용한다.

## 2. 제안하는 사용자 흐름
설정의 계정 삭제 화면에서 대상 계정, 기록·동의 삭제 범위와 되돌릴 수 없음을 안내한다.
현재 이메일/비밀번호 로그인 계정은 비밀번호를 다시 입력하고 삭제 확인을 명시한다. 비밀번호는 HTTPS 요청에만 사용하며 저장·로깅·분석·AI 전송을 하지 않는다.
삭제 버튼은 중복 클릭을 막는다. 계정이 바뀌면 본인 확인 입력과 확인 상태를 비운다.
확정된 성공에만 완료를 표시하고 로컬 세션을 비운다. 응답 유실은 완료 또는 실패로 단정하지 않는다.
이미 처리 중인 삭제 요청은 다른 탭의 계정 전환으로 취소된다고 보장하지 않는다. 승인한 원래 계정에 고정하며 새 계정에는 옛 응답을 반영하지 않는다.
A 삭제가 완료되는 동안 B로 전환된 탭에서 B의 세션을 지우거나 로그아웃시키지 않는다.

## 3. 서버 경계
Next.js 서버 전용 POST /api/account/delete 제안. GET은 삭제하지 않는다.
- same-origin 검사, JSON 콘텐츠 타입·작은 본문 제한·요청 제한. 클라이언트의 owner_id를 관리자 삭제 대상으로 신뢰하지 않는다.
- 요청의 인증을 getUser로 서버 검증한다. 확인 화면의 expectedUid는 일치 검사에만 사용한다. 삭제 대상은 검증된 user.id로 확정한다.
- 별도 비영속 인증 클라이언트로 같은 사용자의 비밀번호를 재확인하고, 반환 UID가 위 UID와 다르면 거부한다. 재인증 토큰을 기존 브라우저 세션과 공유하지 않는다.
- 관리자 클라이언트는 server-only 모듈과 별도 환경 변수에서 생성한다. NEXT_PUBLIC 이름·브라우저 번들·로그에 포함하지 않는다. 관리자 오류 원문·토큰·비밀번호도 출력하지 않는다.
- 사용자 입력으로 Supabase URL이나 키를 선택할 수 없게 한다. 배포의 DB URL과 관리자 키가 같은 프로젝트인지 활성화 전에 검증한다.
- auth.admin.signOut(jwt, 'global') 이후 auth.admin.deleteUser(uid, false)를 제안한다. signOut 실패는 삭제 진행을 막는다. 삭제 실패 시 계정·기록을 먼저 지우지 않는다. 로그아웃만 완료된 부분 실패는 다시 로그인해서 확인한다.
- 기존 외래 키 연쇄 삭제를 사용한다. checkins/consents를 별도 루프로 먼저 삭제하지 않는다. 관리자 삭제 오류·외래 키 실패는 안전한 결과로 반환한다.
- 서버는 성공 응답을 no-store로 반환한다. 건강 기록·이메일·원문 본인 확인 자료를 감사 로그에 남기지 않는다.

## 4. 토큰·삭제 범위의 한계
Supabase의 사용자 삭제·global signOut은 이미 발급한 JWT 자체를 즉시 무효화하지 않는다. 삭제된 사용자로 데이터 재생성이 가능한 모든 경로를 별도로 검증해야 한다.
현재 소스의 사용자 외래 키는 기록·동의 재생성을 제한하지만 이것을 토큰 무효화로 설명하지 않는다.
민감 작업의 즉각 세션 거부를 보장하려면 session_id의 auth.sessions 존재 검사 등이 추가로 필요하다. 이 DB/인증 변경은 본 설계 승인과 구분하고 운영에 임의 적용하지 않는다.
Storage 소유 객체는 Auth 삭제를 막을 수 있다. 현재 소스에는 Storage 사용이 없지만 실제 프로젝트 메타데이터로 확인해야 한다. 운영 파일을 삭제하거나 소유권을 바꾸지 않는다.
백업·관리형 로그의 보존 기간과 삭제 범위는 별도 확인이 필요하다. UI에서 “모든 사본 즉시 영구 삭제”라고 약속하지 않는다.
계정 삭제에 필요한 관리자 키는 프로젝트 전반 권한을 가진다. 공개 키보다 권한이 넓다는 사실을 승인 범위에 명시한다.

## 5. 시험 및 활성화 단계
1. 네트워크 없이 fake admin/auth 클라이언트로 처리 로직을 구현·시험한다. 관리자 키가 없으면 삭제 API는 fail-closed 한다.
2. 임시 PostgreSQL에서 폐기용 C 계정·가상 기록·동의를 만들고 CASCADE, 다른 B 계정 보존, FK 실패 rollback을 시험한다. 실제 Supabase Auth 삭제 검증과 구분한다.
3. 분리 테스트 DB 전용 Preview에만 서버 관리자 키를 지정한다. 기존 운영·전역 Preview 환경 변수는 변경하지 않는다.
4. 테스트 DB의 실제 FK·Storage·기타 사용자 참조 메타데이터를 확인한 뒤 폐기용 C 계정으로 실제 Auth 삭제를 시험한다. 기존 A/B는 삭제하지 않는다.
5. 미인증, 다른 UID, 잘못된 비밀번호, 계정 전환, 중복 클릭, 관리자 실패, 성공 응답 유실, 재로그인 차단, 옛 토큰 생성/수정/조회/삭제, B 보존을 확인한다.
6. 검증 결과와 남은 한계를 정리한 뒤 운영 권한·병합·배포·운영 DB 변경을 각각 필요한 범위로 승인받는다.

## 6. 이번에 필요한 승인
제안: 서버 전용 관리자 클라이언트를 사용하는 코드와 본인 재확인 흐름 구현, 분리 테스트 DB 전용 Preview의 관리자 권한 설정, 별도로 준비한 폐기용 가상 계정만 실제 삭제 시험.
운영 관리자 키 설정·운영 사용자 삭제·운영 DB 변경·운영 배포는 포함하지 않는다.
키·비밀번호를 채팅으로 요구하지 않는다. 실제 설정 단계에서는 서비스의 비밀값 입력 UI를 사용한다.
관리자 권한 설정을 할 수 없으면 fake/임시 DB 시험까지만 진행하고 실제 시험 차단 원인을 기록한다.
