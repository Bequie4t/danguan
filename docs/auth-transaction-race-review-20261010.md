# 분리 TEST 인증 갱신 저장 경쟁 검토

상태: 2026-10-10 23:44 한국시간 사용자 별도 승인 후 분리 TEST 옵트인 구현. 최신 CI/Preview 결과는 PR 설명을 우선한다.

## 재현 근거
설치 auth-js 2.117.3 공개 AuthClient.refreshSession과 가상 토큰/저장소만 사용했다. tests/account-refresh-order.test.ts의 [transaction off reproduction] 2개가 잠금 없이 실행되는 문제 동작을 명시적으로 확인한다. 이 두 테스트 통과는 보호 성공이 아니라 대조 결함 재현 성공이다. 실계정/DB 시험으로 해석하지 않는다.

1. 성공 갱신: SDK가 storedAfter를 읽어 기존 A와 같다고 판단한 뒤 _saveSession의 실제 storage.setItem 경계에서 B로 바뀌면 A 결과가 B를 덮어쓴다. TOKEN_REFRESHED도 발생한다. 기존 보호는 저장 전에 계정이 바뀐 경우는 버리지만 이 구간을 원자적으로 묶지 않는다.
2. 실패 갱신: opt-in 패치가 storedNow에서 만료된 A를 확인한 뒤 _removeSession의 storage.removeItem 경계에서 B로 바뀌면 B가 제거되고 SIGNED_OUT이 발생한다. 앞선 패치의 변경 주체 비교만으로 검사와 제거 사이를 묶지 않는다.

가상 저장소 훅은 읽기/검사 이후 저장/제거 경계의 교차 실행을 결정적으로 재현한다. 실제 Chromium SSR의 현재 cookie Web Lock 큐까지 재현한 것은 아니다. 기존 잠금은 setAll/정리만 묶고 앞선 SDK 저장소 읽기/검사와 같은 트랜잭션으로 묶지 않으므로 남은 위험을 검토해야 한다.

## 승인 요청할 구체 변경안
- 별도 분리 TEST Preview 옵트인에서 브라우저 SDK의 공개 auth.lock 옵션으로 인증 작업 전체(읽기/갱신/저장/정리)를 같은 프로젝트 잠금 아래 실행한다. cookie setAll만 잠그는 방식과 구분한다.
- 직접 작성하는 가입 확인 세션 저장과 삭제 후 인증 정리도 같은 인증 작업 잠금에 참여하고 기존 cookie 잠금은 안쪽에서 같은 순서로 얻는다. SDK 호출을 잠금 안에 재진입시켜 교착시키지 않도록 경로를 분리한다.
- 잠금 대기 제한/사용 불가 시 실패로 반환하고 다른 작업 잠금을 강제로 빼앗지 않는다. 설치 SDK navigatorLock은 시간 초과 뒤 stealing 경로가 있어 그대로 사용하지 않는다. 비밀 토큰/코드/비밀번호를 잠금 이름이나 로그에 넣지 않는다.
- 기존 계정 자신의 만료 세션 정리는 유지한다. 로그인 실패를 성공으로 합성하지 않고 실제 B 로그인을 A 인증으로 재전송하지 않는다.
- 기본 꺼짐, 정확한 TEST DB/승인된 Preview 옵트인으로 한정한다. 운영 활성화/권한 확대/새 라이브러리/운영 DB 변경 없음.

## 승인 후 검증할 항목
성공 저장/실패 제거 경계에 B 전환을 큐잉하여 실제 저장 값과 인증 이벤트를 대조한다. B 로그인·콜백·삭제 정리의 참여를 확인한다. 같은 계정 갱신, 본래 A 만료 거부 정리, 잠금 시간 초과와 없는 브라우저, 중복 클릭/취소, 기존 기록 화면 회귀를 확인한다. 단위의 명시 결함 재현과 보호 시험을 함께 두어 오인하지 않는다. 실제 Chromium 쿠키 큐 시험 후에도 실계정/구버전 탭/비협력 서버/다른 기기 범위는 별도로 남긴다.

## 범위와 한계
협력하지 않는 구버전/서버 쿠키 작성자와 다른 기기를 Web Lock으로 직렬화할 수 없으며 운영 준비 완료로 판정하지 않는다. SDK 내부 성공/실패 경로를 추가 패치하지 않고 공개 lock 옵션과 공통 작성자 참여를 사용한다. SDK lock 옵션은 deprecated이며 v3 제거 예정 안내가 있어 SDK 업데이트 시 재설계가 필요하다.

## 승인 후 구현과 검증
NEXT_PUBLIC_TEST_AUTH_TRANSACTION_LOCK_ENABLED=true와 정확한 TEST DB에서만 적용한다. 이 공개 옵트인 플래그는 해당 작업 브랜치 Preview 환경에만 설정했다. 기본/운영 DB는 기존 인증을 유지한다. SDK에 strictAuthLock을 전달하고 lock:프로젝트저장키 이름을 사용한다. SDK 내부 잠금이 없는 password sign-in/sign-up은 초기화를 잠금 밖에서 기다린 뒤 같은 잠금 안에서 실행한다. 콜백의 시작 스냅샷 확인/최종 저장과 삭제 후 로컬 쿠키 정리도 같은 인증 잠금→cookie 잠금 순서를 따른다. 별도 메모리 PKCE 코드 교환 네트워크는 잠금 밖에서 실행하고 최종 스냅샷을 다시 확인한다.
대기는 기본 5초/최대 15초로 제한하며 실행 중 작업을 강탈하지 않는다. 잠금 미지원/대기 실패는 인증 실행을 거부한다. 옵트인 로그아웃 실패는 완료 화면으로 이동시키지 않고 재시도 안내를 표시한다. 서버 키/권한 변경 없음.
로컬 단위 102개(잠금 꺼짐 결함 대조 2개 포함)·타입·빌드 통과. SDK 가상 저장소에서 A 성공 저장/실패 제거 경계에 실제 공개 password sign-in B를 큐잉하여 최종 B와 마지막 SIGNED_IN을 확인했다. Chromium 시험에 실제 SSR 쿠키 어댑터·Web Locks·SDK 로그인 경계 2개 및 직접 callback/cleanup 작성자 참여 2개를 추가했다. 실제 Chromium 실행 결과는 CI 확인 전이며 실계정 검증과 구분한다.

ChatGPT가 재현 코드와 자체 검토를 수행했다. 독립 보안 검토가 아니다.
